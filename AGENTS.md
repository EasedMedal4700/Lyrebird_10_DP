## Lyrebird specifics

### Database (Supabase)

The process reads and writes a self-hosted Supabase (`http://tower:8000`, Postgres schema `lyrebird`)
through `Workflows/Supabase/GetConnection.xaml`, `GetRows.xaml` and `UpdateRows.xaml`
(HTTP Request activity, PostgREST API). Use those workflows; don't add Invoke Code or Config.xlsx entries for this.

When you need the database structure (tables, columns, allowed status values, constraints), use either source:

- **Supabase itself**: the live database is the source of truth. Query it, for example by running `GetRows.xaml`.
- **The shared `DB` folder** `../Lyrebird_00_Shared/DB` (relative to this project folder; it is part of the
  `Lyrebird` parent repository, not of this project's repository): one `<table>.sql` file per table with its
  `create table` statement (for example `../Lyrebird_00_Shared/DB/wishlist.sql`).
  Don't use absolute paths: the user folder differs per machine.

If the `DB` folder doesn't exist, a table is missing from it, or its contents don't match what Supabase returns,
**tell the user** which table is missing or what differs. Don't silently work around it.
The user will then give you the current DDL so you can create or update the file.

### Orchestrator assets

Process assets live in the Orchestrator folder **`Lyrebird`** (not `Shared/Lyrebird`) and are named `10_DP_<Name>`.
Lyrebird assets used by several processes live in folder **`Lyrebird`** with prefix **`00_SH_`** (since 2026-10-08,
see `../Lyrebird_20_PF_Download/Documentation/Shared_Assets_Migration.md`). The older folder **`Shared`** (no prefix)
still holds `PersonalEmail`.

Used by the source (`Workflows/Supabase/GetConnection.xaml`, `Workflows/MusicBrainz/GetUserAgent.xaml`):

| Asset | Type | Purpose |
|---|---|---|
| `00_SH_SupabaseUrl` | Text | Supabase base URL (shared with 20_PF) |
| `00_SH_SupabaseApiKey` | Secret | Supabase API key (shared with 20_PF); read with Get Secret right before each request |
| `10_DP_MusicBrainzUserAgent` | Text | App name/version for the MusicBrainz User-Agent (`Lyrebird_10_DP/1.0.0`); missing/empty stops the job at startup |
| `PersonalEmail` (folder `Shared`) | Text | Contact email; `ValidateAlbum.xaml` sends `<10_DP_MusicBrainzUserAgent> ( <PersonalEmail> )` as User-Agent; missing/empty only warns |

Deprecated, kept on purpose (do not delete): `10_DP_SupabaseUrl`, `10_DP_SupabaseApiKey` (still read by the **published**
package 26.10.0 until 10_DP is republished; rollback). Not read by any workflow: `10_DP_DataFolder` (10_DP needs no data
root), `10_DP_SlsknetLogin` (Soulseek login; no process logs in).

## Conventions

- **Workflow class**: `x:Class` = folder path with `_` separators (e.g. `Workflows_Supabase_GetRows`)
- **File naming**: PascalCase verb-noun (`GetRows`, `ValidateAlbum`), grouped in `Workflows/<System>/` subfolders
- **Arguments**: `in_` / `out_` / `io_` prefixes, PascalCase names; every argument has an `Annotation.AnnotationText` description; defaults via `this:<Class>.<arg>="..."` on the root element
- **Variables**: PascalCase (`RequestUrl`, `StatusCounts`, `LogText`)
- **Root container**: `Sequence` with descriptive DisplayName; activities named by intent ("Log rows read", "If Supabase returned an error")
- **Invoke paths**: backslash, project-relative (`Workflows\Supabase\GetConnection.xaml`); in `project.json` test paths are `Tests\\<Name>.xaml`
- **Strings**: VB interpolated strings `$"..."`
- **JSON fields**: read null-safe with `row.Value(Of String)("artist")` (returns Nothing for a missing/null field), not `row("artist").ToString`
- **Error handling**: guard `If` + `Throw New Exception($"...")` on missing assets / non-success HTTP; catch only the exceptions you can classify and `Rethrow` the rest
- **Secrets**: API key read with `GetSecret` right before the HTTP Request; see "Known issues" for ST-SEC-009
- **Logging**: `LogMessage` Info for milestones, Warn/Error for problems; carry the queue Reference / wishlist id in every per-item line
- **No Invoke Code**, no Config.xlsx entries for Supabase (assets instead); queue names live in Config.xlsx and can be overridden by Main arguments

## Architecture

- **Pattern**: REFramework with Orchestrator queue transactions. `MaxRetryNumber = 0` (no local retry; Orchestrator retries, queue max 2), `MaxConsecutiveSystemExceptions = 5`, `ShouldMarkJobAsFaulted = True`
- **Data flow**: Supabase `lyrebird.wishlist` (status `new`) → startup load (`LoadNewWishlistItems`, once per job) → queue `Lyrebird_Validate` → Get Transaction Data → `Process.xaml` → `ProcessValidateQueueItem` → queue `Lyrebird_Wishlist` + guarded status write-back via `UpdateRows`
- **Run safety**: test mode = `_IT` input queue; then the output must be `_IT` and only `LYREBIRD_IT` rows are loaded; production never loads `LYREBIRD_IT` rows nor writes to `_IT` queues. Both queues must enforce unique references (checked at startup with GetQueueSettings)
- **Timing**: `LastRequestUtc` lives in Main for the whole job (InOut to Process); set to now after a failed transaction
- **Statuses written**: only existing ones (`queued`, `check_spelling`, `not_found`, `failed`). Release ambiguity = `check_spelling` with `RELEASE_CHOICE:` message (a person sets `chosen_release_id` and resubmits); duplicate album = `failed` with `DUPLICATE:` message; exhausted technical retries without a download item = `failed` with `TECHNICAL:` message. Never write `api_error`.
- **Release policy**: `chosen_release_id` if set; otherwise exactly one Official release in the earliest year, else ambiguous (no tie-breaker). In practice every real album needs `chosen_release_id` once.
- **Duplicate albums**: column `reserved_release_group` + partial unique index `wishlist_reserved_release_group_uniq`, claimed before enqueue (409/23505 → duplicate), released on every non-queued outcome and on exhausted retries without a download item.
- **Schema**: migrations `2026-10-07_01_wishlist_part2.sql` and `2026-10-07_02_wishlist_queue_reference.sql` applied; `mbid` = release GROUP.
- **Idempotency**: readable queue Reference `<artist> - <album> | WL-<id>-S<submission>` (same in both queues), persisted on the row once per submission before enqueueing and reused unchanged + "Enforce unique references" (case-insensitive); recovery reads an existing item and requires its `Request*` fields to match the row; see `Documentation/Lyrebird_DataContract.md`
- **Queues** (folder Lyrebird, no triggers): `Lyrebird_Validate`, `Lyrebird_Wishlist` (production), `Lyrebird_Validate_IT` / `Lyrebird_Wishlist_IT` (component tests, no retry), `Lyrebird_Validate_Main_IT` / `Lyrebird_Wishlist_Main_IT` (Main tests, production retry settings)
- **External integrations**: self-hosted Supabase REST (PostgREST), MusicBrainz WS/2 (JSON, User-Agent from assets), Orchestrator folders `Lyrebird` and `Shared`

## Known issues

- Analyzer rule **ST-SEC-009** (Error): `GetRows.xaml` and `UpdateRows.xaml` convert the Supabase key from SecureString to String for the `apikey` / `Authorization` headers (no activity accepts a SecureString header). The owner **accepted this risk** (2026-10-06, `Documentation/Lyrebird_DataContract.md` section 9). The exception is recorded in `Governance/Lyrebird_10_DP.analyzer-policy.json` (all default rules; only ST-SEC-009 gets `Excluded = UiPath.Web.Activities.Http.NetHttpRequest`); build with that file. A plain `uip rpa build .` still reports the two accepted findings.
- Never add another SecureString-to-String conversion: `Tests/SecureStringConversionGuardTestCase.xaml` fails if any other workflow does it. Keep the robot log level for this process below Verbose.
- A killed job leaves its current item In Progress; it is abandoned after 24 h and not retried (`RetryAbandonedItems = No`); the row then needs a resubmission (DataContract limitations).
