## Conventions

- **Workflow class**: `x:Class` = folder path with `_` separators (e.g. `Workflows_Supabase_GetRows`)
- **File naming**: PascalCase verb-noun (`GetRows`, `ValidateAlbum`), grouped in `Workflows/<System>/` subfolders
- **Arguments**: `in_` / `out_` / `io_` prefixes, PascalCase names; every argument has an `Annotation.AnnotationText` description; defaults via `this:<Class>.<arg>="..."` on the root element
- **Variables**: PascalCase (`RequestUrl`, `StatusCounts`, `LogText`)
- **Root container**: `Sequence` with descriptive DisplayName; activities named by intent ("Log rows read", "If Supabase returned an error")
- **Invoke paths**: backslash, project-relative (`Workflows\Supabase\GetConnection.xaml`)
- **Strings**: VB interpolated strings `$"..."`
- **JSON fields**: read null-safe with `row.Value(Of String)("artist")` (returns Nothing for a missing/null field), not `row("artist").ToString`
- **Error handling**: guard `If` + `Throw New Exception($"...")` on missing assets / non-success HTTP; catch only the exceptions you can classify and `Rethrow` the rest
- **Secrets**: API key read with `GetSecret` right before the HTTP Request; see "Known issues" for ST-SEC-009
- **Logging**: `LogMessage` Info for milestones, Warn/Error for problems; carry the queue Reference / wishlist id in every per-item line
- **No Invoke Code**, no Config.xlsx entries for Supabase or queue settings (assets and arguments instead)

## Architecture

- **Pattern**: REFramework with an Orchestrator queue as transaction source; the Lyrebird workflows are not wired into `Main.xaml` yet
- **Data flow**: Supabase `lyrebird.wishlist` (status `new`) → `LoadNewWishlistItems` → queue `Lyrebird_Validate` → `ProcessValidateQueueItem` (via `RunValidateBatch`; step 3 = call it from `Process.xaml`) → queue `Lyrebird_Wishlist` + guarded status write-back via `UpdateRows`
- **Statuses written**: only existing ones (`queued`, `check_spelling`, `not_found`, `failed`). Release ambiguity = `check_spelling` with `RELEASE_CHOICE:` message (a person sets `chosen_release_id` and resubmits); duplicate album = `failed` with `DUPLICATE:` message. Never write `api_error`.
- **Release policy**: `chosen_release_id` if set; otherwise exactly one Official release in the earliest year, else ambiguous (no tie-breaker). In practice every real album needs `chosen_release_id` once.
- **Duplicate albums**: column `reserved_release_group` + partial unique index `wishlist_reserved_release_group_uniq`, claimed before enqueue (409/23505 → duplicate), released on every non-queued outcome.
- **Schema**: migrations `2026-10-07_01_wishlist_part2.sql` (`submission`, `mb_release_id`, `mb_artist_id`, `chosen_release_id`, `reserved_release_group`) and `2026-10-07_02_wishlist_queue_reference.sql` (`queue_reference`, max 128) applied; `mbid` = release GROUP. Columns are still detected from the `select=*` row.
- **Idempotency**: readable queue Reference `<artist> - <album> | WL-<id>-S<submission>` (same in both queues), persisted on the row once per submission before enqueueing and reused unchanged + "Enforce unique references" (case-insensitive) on `Lyrebird_Validate`, `Lyrebird_Wishlist` and their `_IT` test copies (folder Lyrebird); recovery reads an existing item and requires its `Request*` fields to match the row; see `Documentation/Lyrebird_DataContract.md`
- **External integrations**: self-hosted Supabase REST (PostgREST), MusicBrainz WS/2 (JSON, User-Agent from assets), Orchestrator folders `Lyrebird` and `Shared`

## Known issues

- Analyzer rule **ST-SEC-009** (Error): `GetRows.xaml` and `UpdateRows.xaml` convert the Supabase key from SecureString to String for the `apikey` / `Authorization` headers (no activity accepts a SecureString header). The owner **accepted this risk** (2026-10-06, `Documentation/Lyrebird_DataContract.md` section 9). The exception is recorded in `Governance/Lyrebird_10_DP.analyzer-policy.json` (all default rules; only ST-SEC-009 gets `Excluded = UiPath.Web.Activities.Http.NetHttpRequest`); build with that file. A plain `uip rpa build .` still reports the two accepted findings.
- Never add another SecureString-to-String conversion: `Tests/SecureStringConversionGuardTestCase.xaml` fails if any other workflow does it. Keep the robot log level for this process below Verbose.
